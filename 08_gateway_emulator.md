       # Эмулятор платёжного шлюза — кейс 1

## 1. Сценарии

Эмулятор имитирует ответ банка. Сервис передаёт ему order_id, amount и currency. Эмулятор определяет результат по order_id.

| № | Условие выбора | Результат | error_code | Задержка |
|---|---|---|---|---|
| 1 | hash(order_id) mod 10 = 0–6 | SUCCESS | — | 0–2 с |
| 2 | hash(order_id) mod 10 = 7 | DECLINED | INSUFFICIENT_FUNDS | пока не определена |
| 3 | hash(order_id) mod 10 = 8 | DECLINED | CARD_DECLINED | пока не определена |
| 4 | hash(order_id) mod 10 = 9 | TIMEOUT | TIMEOUT | больше времени ожидания сервиса |

В первых трёх случаях эмулятор возвращает результат обработки. В четвёртом случае он не отвечает вовремя. В PayShield платёж остаётся в PENDING, потому что результат оплаты неизвестен.

TIMEOUT в таблице — результат сценария эмулятора, а не отдельный статус платежа из Data Dictionary.

## 2. Правила детерминизма

Вопрос: почему один и тот же order_id должен всегда давать один и тот же результат?

Ответ: Чтобы при повторном запросе эмулятор не выдавал разные результаты для одного заказа. Это помогает проверять работу сервиса и избегать путаницы при повторных запросах.

Вопрос: как проверить, что эмулятор детерминирован?

Ответ: Несколько раз отправить один и тот же order_id и сравнить результаты. Для одинакового order_id результат должен совпадать. Затем проверить несколько разных order_id для всех четырёх сценариев.

В прототипе 05_app.py используется md5 от order_id, после чего вычисляется остаток от деления на 10. При одинаковом order_id получится одно и то же число.

## 3. Логирование

Какие поля пишет эмулятор в gateway.log?

| Поле | Пример | Зачем |
|---|---|---|
| timestamp | 2026-11-05T12:00:00Z | Чтобы знать время запроса |
| order_id | ord_1001 | Чтобы понимать, к какому заказу относится запрос |
| correlation_id | corr_0038 | Чтобы найти связанные записи в логах |
| result | SUCCESS | Чтобы видеть результат обращения к эмулятору |
| error_code | INSUFFICIENT_FUNDS | Чтобы видеть причину отказа, если она есть |
| duration_ms | 850 | Чтобы видеть, сколько времени заняла обработка |

В лог записываем и успешные операции, и отказы, и таймауты. Поля таблицы — предлагаемый формат лога для согласования. Данные карты, SMS-коды и токены подтверждения в лог не записываем.

## 4. Вход и выход

Сервис обращается к эмулятору через POST /gateway/charge.

Пример запроса:

```json
{
  "order_id": "ord_1001",
  "amount": 1500.00,
  "currency": "RUB"
}
```

Пример ответа при успешной оплате:

```json
{
  "status": "SUCCESS",
  "error_code": null
}
```

Пример ответа при отказе:

```json
{
  "status": "DECLINED",
  "error_code": "INSUFFICIENT_FUNDS"
}
```

Если эмулятор не ответил вовремя, PayShield прекращает ожидание ответа, но оставляет платёж в PENDING. Это нужно, потому что неизвестно, успел ли эмулятор обработать запрос. Повторное списание без проверки результата делать нельзя.

Структура ответов выше предлагается для HTTP-версии эмулятора. В текущем 05_app.py эмулятор работает как функция Python и возвращает status и error_code. Сам POST /gateway/charge там ещё не реализован.
