# 07_confirmation.md — подтверждение платежа

## 1. Целевой сценарий подтверждения

1. Клиент вызывает `POST /api/v1/payments` и передаёт данные платежа.
2. Сервис проверяет данные и создаёт платёж со статусом `CREATED`.
3. Сервис выдаёт одноразовый `confirm_token` со сроком действия 10 минут.
4. Клиент вызывает `POST /api/v1/payments/{id}/confirm`.
5. Сервис проверяет токен, его срок, одноразовость и связь с `payment_id`, затем обращается к эмулятору.
6. Результат эмулятора переводит платёж в `SUCCESS`, `DECLINED` или `PENDING`.

## 2. Требования к токену

- Срок действия: 10 минут (600 секунд) с момента выдачи.
- Токен одноразовый.
- На сервере хранится только криптографический хеш токена, а не исходное значение.
- Запись токена связана с `payment_id`, временем истечения и признаком использования.
- Истёкший или использованный токен не должен инициировать обращение к шлюзу.
- Повтор того же запроса с тем же `Idempotency-Key` возвращает сохранённый ответ, не вызывая повторного обращения к шлюзу.

## 3. Методы подтверждения из проектного задания

| Метод | Назначение | Ограничение |
|---|---|---|
| `card_token` | Подтверждение с тестовым токеном карты | Настоящие данные карты не принимаются и не хранятся |
| `sms_code` | Имитация подтверждения SMS-кодом | До 3 попыток; реальная SMS-рассылка не требуется |
| `biometric_stub` | Заглушка биометрического подтверждения | Реальное сканирование биометрии не выполняется |

## 4. Коды и переходы

| Ситуация | Ожидаемое поведение |
|---|---|
| Токен истёк | Отклонить подтверждение, HTTP 410; платёж остаётся `CREATED` до отдельного решения о новом токене |
| Токен уже использован | Отклонить новое подтверждение, HTTP 410 |
| Неверный токен или токен другого платежа | HTTP 422; шлюз не вызывается |
| Три неверных SMS-кода | Заблокировать подтверждение; статус самого платежа требует отдельного решения команды |
| Шлюз вернул отказ | `DECLINED`, HTTP 402 |
| Шлюз не ответил вовремя | `PENDING`, HTTP 504; не выполнять повторное списание автоматически |
| Точный повтор с тем же ключом | Вернуть сохранённый ответ, HTTP 200 |

## 5. Статус реализации

**ОПИСАНО В ЦЕЛЕВОМ КОНТРАКТЕ, НЕ РЕАЛИЗОВАНО В CLI.** В предоставленном `05_app.py` нет генерации и хеширования `confirm_token`, SMS-кода, биометрической заглушки и отдельных HTTP-обработчиков. CLI-прототип выполняет проверку входа и сразу запускает детерминированный эмулятор. Нельзя представлять этот CLI как полностью реализованный двухфазный процесс подтверждения.

## 6. Зафиксированные решения версии 1.0.0

1. Истёкший или использованный `confirm_token` даёт HTTP 410; обращение к шлюзу не выполняется, платёж остаётся `CREATED`.
2. После трёх неверных SMS-кодов блокируется текущая попытка подтверждения. Платёж не становится `DECLINED`, поскольку платёжный шлюз не обрабатывал операцию.
3. Повторная выдача токена в версии 1.0.0 не предоставляется.
4. Доступ к операциям над платежом в целевом API требует Bearer-аутентификации; проверка прав владельца выполняется серверным слоем авторизации.
5. После таймаута платёж остаётся `PENDING`. Клиент может запросить статус отдельным `GET`; автоматическое повторное списание запрещено.

**Граница реализации:** эти правила описывают целевую спецификацию. В CLI-версии 1.0.0 токены, SMS, Bearer-аутентификация и HTTP-маршруты не реализованы.
