# 04_requirements.md — требования к PayShield

## 1. Функциональные требования

| ID | Требование | Приоритет | Проверка |
|---|---|---|---|
| FR-1 | Создать платёж по `order_id`, `recipient`, `purpose`, `amount`, `currency` | Must | T1-1 |
| FR-2 | Проверять обязательность входных полей | Must | T1-3 |
| FR-3 | Проверять `order_id` по `^ord_[0-9]{4}$` | Must | T1-3 |
| FR-4 | Проверять диапазон и точность суммы | Must | T1-3 |
| FR-5 | Разрешать только валюту `RUB` | Must | T1-3 |
| FR-6 | Разрешать только активного получателя из `recipients.csv` | Must | T1-3 |
| FR-7 | Проверять длину назначения и отсутствие PAN/CVV | Must | T1-3 |
| FR-8 | Не создавать второй платёж для пары `order_id + recipient` | Must | Регрессионный тест `test_duplicate_order_different_key` |
| FR-9 | Обеспечивать идемпотентность по `Idempotency-Key` в течение 24 часов | Must | T1-4, T1-5 |
| FR-10 | Отменять платёж до подтверждения | Should | Отдельный тест отмены; в предоставленном наборе T1-1…T1-5 не выделен |

## 2. Нефункциональные требования

| ID | Требование | Статус проверки |
|---|---|---|
| NFR-1 | Целевой ответ API создания платежа ≤ 2 с без учёта задержки шлюза | Не измерялось; HTTP-сервер отсутствует |
| NFR-2 | Время локальной валидации ≤ 100 мс | Целевой показатель; требуется отдельный замер |
| NFR-3 | Операции журналируются с `correlation_id` | Частично реализовано в CLI: service log и gateway log; покрытие нужно проверить |
| NFR-4 | Токены подтверждения хранятся только в виде хеша | Требование целевого API; токены в CLI-прототипе пока не реализованы |
| NFR-5 | Доступность сервиса ≥ 99,5% в месяц | Целевой показатель эксплуатации; для локального CLI не измерим |
| NFR-6 | `purpose` ≤ 200 символов, `order_id` соответствует regex | Реализовано в CLI |

## 3. Ограничения

1. Реальный эквайринг не подключается; используется детерминированный эмулятор.
2. Наборы CSV содержат учебные/синтетические данные.
3. CLI-прототип не является HTTP-сервером и не предоставляет сетевые маршруты.
4. В CLI ключ идемпотентности передаётся в JSON как `idempotency_key`; в целевом API — заголовком `Idempotency-Key`.
5. Двухфазное подтверждение с `confirm_token`, SMS и биометрической заглушкой описано в целевой спецификации, но не реализовано в `05_app.py`.

## 4. Пользовательские сценарии

### Сценарий 1. Успешная оплата
1. Пациент выбирает услугу и нажимает «Оплатить».
2. Система показывает сумму и назначение платежа.
3. Пациент подтверждает операцию.
4. Пациент видит сообщение об успешной оплате.

### Сценарий 2. Отказ
1. Пациент инициирует оплату.
2. Система получает отказ платёжного шлюза.
3. Пациент видит понятную причину отказа и может выбрать другой способ оплаты.

### Сценарий 3. Некорректные данные
1. Пациент инициирует оплату с неверной суммой или реквизитом получателя.
2. Система сообщает, какое поле нужно исправить.
3. Пациент исправляет данные и повторяет попытку.

### Сценарий 4. Повторная отправка
1. Из-за задержки сети пациент повторно отправляет тот же запрос.
2. Система распознаёт тот же `Idempotency-Key`.
3. Пациент получает ранее сохранённый ответ; второй платёж не создаётся.

### Сценарий 5. Неопределённый результат
1. Пациент инициирует оплату.
2. Ответ шлюза не поступает вовремя.
3. Пациент видит состояние «В обработке».
4. Система не инициирует повторное списание без проверки результата.
